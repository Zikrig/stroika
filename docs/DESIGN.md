# Дизайн-документ: Система учёта заявок (Telegram-бот)

## 1. Цели и контекст

### 1.1 Проблема

**Дублирующие заявки**: на объекте возникает потребность в материалах; прораб сообщает в ПДО; по цепочке идёт проверка склада, закупка, частичные поставки. Прораб не видит единой картины («что уже едет», «что в закупке», «что получено») и создаёт повторные запросы («ещё 2700 м», «ещё 2200 м»). В итоге компания закупает в разы больше необходимого.

**Причины**:
- нет единого «паспорта» потребности;
- нет наглядных цифр: в процессе / в пути / получено;
- нет правил корректировки;
- коммуникация размазана по звонкам и мессенджерам.

### 1.2 Цель системы

Инструмент, который делает потребность **видимой** всем и всегда: что запросили, что на складе, что в закупке, что отгружено, что получено, что осталось. История неизменяема («тихо переписать» нельзя).

### 1.3 Выбранный подход

**Мессенджер + правила**: Telegram как среда работы, бот с жёсткими правилами — чат становится системой учёта, а не просто перепиской.

---

## 2. Архитектура

### 2.1 Модель «объект — группа»

- **Один объект** = одна служебная Telegram-группа.
- Прораб создаёт **заявку** (сырой сигнал потребности); бот присваивает уникальный **ID** (формат: `IG-XX`, для дочерних: `IG-XX-N`).
- ПДО **всегда вручную** формализует заявку (Excel + сверка с 1С/складом).
- При нескольких позициях в Excel:
  - создаётся **контейнер** (информационный пост);
  - создаются **дочерние заявки** (каждая позиция отдельно).
- **Жизнь заявки** = история событий, читаемая сверху вниз; каждое действие — новое сообщение с полным паспортом и динамическим блоком.

### 2.2 Интеграция с Google Таблицей

- Служебная группа **синхронизируется** с Google Таблицей — сквозной журнал событий.
- Каждое действие в Telegram (создание, формализация, передача в закупку, отгрузка, получение, отмена, пауза, комментарий руководителя) фиксируется **отдельной строкой** в таблице.
- Таблица: сквозной лог, контроль, аналитика, база для будущей интеграции с 1С.
- Для таблицы как системы обязательно: **тип события**, **дельта изменения**, **роль, совершившая действие**.
- Редактирование записей в таблице вручную **запрещено** (настройками среды).

### 2.3 Главный принцип

**Ничего не переписывается.** Любое действие любой роли публикует **новое сообщение** по тому же ID с:
- полным паспортом;
- полным динамическим блоком.

История дублируется в Telegram и в Google Таблице и защищена от тихих правок.

## 3. Структура сообщения по заявке

Каждое состояние публикуется как одно сообщение.

### 3.1 Паспорт (всегда полностью)

| Элемент | Описание |
|--------|----------|
| ID заявки | IG-XX или IG-XX-N |
| 👷 Прораб | ФИО/контакт |
| 🏗 Объект | Название объекта |
| 🎯 Подобъект (цель) | Подобъект/цель |
| 📦 Номенклатура 1С | Наименование по 1С |
| 🔢 Код 1С | Код номенклатуры |
| 📏 Количество (Запрошено) | Число + ед. изм. |
| 📅 Требуется до | Срок потребности |
| 🕒 Дата создания | Дата/время создания |

### 3.2 Динамический блок (всегда полностью)

| Элемент | Описание |
|--------|----------|
| Статус | 🔴 / 🟡 / 🔵 / ⚪ / ⚫ / ⛔ |
| Этап | Текстовое описание этапа |
| 👤 Ответственный | Роль/ФИО |
| 📦 Потребность | Запрошено / Со склада / В закупку |
| 🚚 Закупка | Ожидаемые даты, отгрузка, поставка на объект |
| 📍 На объекте | Получено (итого) / Остаток |

### 3.3 Цветовая логика статусов

| Статус | Значение |
|--------|----------|
| 🔴 | Ждёт действия |
| 🟡 | В работе |
| 🔵 | Передано дальше |
| ⚪ | Закрыто |
| ⚫ | Отменено |
| ⛔ | Приостановлено руководителем |

Шарик = стадия процесса; ответственный = человек.

## 4. Структура записи в Google Таблице

Каждое **событие** по заявке — отдельная строка.

### 4.1 Обязательные поля

- ID заявки
- Родительский ID (если дочерняя от контейнера)
- Кто согласовал
- Объект
- Прораб
- Подобъект
- Наименование от прораба
- Наименование по 1С
- Код 1С
- Запрошено
- Ед. изм.
- Со склада
- В закупку
- Статус
- Этап
- Ответственный
- **Тип события**
- Количество получено (дельта)
- Итог получено
- Остаток
- Дата и время события
- Роль, совершившая действие

**Важно**: таблица хранит историю; актуальное состояние — последняя запись по ID.

## 5. Контейнер

Если Excel содержит **несколько позиций**, исходная заявка становится контейнером.

- Заголовок: `📦 КОНТЕЙНЕР IG-XX`.
- Текст: «Сформирован из файла IG-XX.xlsx», «Разбит ПДО на заявки: IG-XX-1, IG-XX-2».
- **Правила**: без динамики, без кнопок, не участвует в статусах; только для понимания происхождения дочерних заявок.

## 6. Роли и сценарии

### 6.1 Прораб

- **Задача**: заявить потребность; подтвердить получение.
- **Кнопки**: «Получено частично», «Получено полностью», «Повторить заявку».
- **Правило**: не переписывает старую заявку и не создаёт новую из-за частичной поставки.

### 6.2 ПДО

- **Задача**: сверить остатки; формализовать заявку через Excel; разделить «со склада» / «в закупку».
- **Excel-форма** (поля): ID (бот), Согласовано с руководителем стройки, Дата/время заявки, Дата потребности, Подобъект, Прораб, Наименование от прораба, Наименование по 1С, Код 1С, Запрошено, Ед. изм., Со склада, В закупку.
- **Правило**: Запрошено = Со склада + В закупку; ID не заполняется вручную; «Наименование по 1С» и «Код 1С» обязательны для 1С.

### 6.3 Закупка

- **Вход в процесс**: заявка передаётся в закупку после ПДО; закупка нажимает «К заявке», и заявка сразу переходит в «В работе / Закупка в работе».
- **В работе**: «Закуплено» (после нажатия — кнопка «Укажите срок»), «Вернуть ПДО», «Отменить».
- **После «Закуплено»**: «Отгружено» (после нажатия — «Укажите срок»), «Вернуть ПДО».
- **После «Отгружено»**: кнопок нет; ответственный становится прораб.

### 6.4 Руководитель

- Видит всё.
- Может: комментарий, пауза, снять паузу, полностью Отменить заявку.
- Любое действие — новое сообщение с полным паспортом, динамическим блоком и управленческим комментарием.

### 6.5 Зритель

- Видит всё; кнопок нет; в процесс не вмешивается.

### 6.6 Право отмены

- **Прораб** — отмена только до передачи в ПДО.
- **ПДО** — до передачи в закупку.
- **Закупка** — до «Закуплено».
- После выхода из зоны ответственности кнопка «Отменить» исчезает.
- **Отмена**: новое сообщение, полный паспорт, динамический блок, статус ⚫ «Отменено», обязательный комментарий; заявка закрывается навсегда.

### 6.7 Команда `/admin` для определения роли

- Команда доступна только администраторам служебной Telegram-группы.
- По команде `/admin` бот определяет роль пользователя в текущей группе и отвечает в личном сообщении:
  - «Ваша роль: Прораб» / «Ваша роль: ПДО» / «Ваша роль: Закупка» / «Ваша роль: Руководитель» / «Ваша роль: Зритель».
- Если роль для этого пользователя в группе не назначена, бот возвращает: «Роль не назначена. Обратитесь к руководителю или администратору группы».
- Если пользователь не является администратором группы, бот возвращает: «Команда доступна только администраторам группы».
- Если у пользователя назначено более одной роли, бот возвращает ошибку конфигурации и просит оставить только одну активную роль.

---

## 7. Защитные механизмы

1. Нет редактирования — только события (новые сообщения).
2. Паспорт и динамика всегда вместе в одном сообщении.
3. Контейнер не участвует в статусах и кнопках.
4. Прораб фиксирует получение только кнопками.
5. Пауза и прекращение — только через руководителя.
6. Зрители не вмешиваются.
7. Нештатные ситуации — личное общение + отмена на этапе обработки с последующим созданием новой заявки.
8. Все события фиксируются в Google Таблице как неизменяемый журнал.

---

## 8. Нефункциональные требования (для реализации)

- **Надёжность**: сохранение всех событий; повторная отправка в таблицу при сбоях.
- **Идентификация**: привязка пользователя Telegram к роли в группе (по списку ролей/настроек) с проверкой через команду `/admin`.
- **Безопасность**: только участники группы с назначенными ролями могут выполнять действия; зрители — только просмотр.
- **Масштабирование**: один бот — много групп (объектов); изоляция данных по группе.

Документ можно использовать как основу для технического задания на разработку бота (aiogram) и синхронизации с Google Таблицей, а также для развёртывания в Docker.
